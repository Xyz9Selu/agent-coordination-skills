## #2 · 交接提醒的两条门槛（2026-10-21）

**证据：** 2026-10-21 的一份一周用量报告里，一个连开 6 天的 coordinator 会话单独占了一周 token 的 22.6%，5184 次调用

同一份报告里，那个长会话 38 次大的缓存重写有 28 次发生在空闲超过 60 分钟之后，每次重写 70–94 万 token；换一个新会话，

**推翻条件：** 缓存有效期不再是一小时（改 60 分钟那条）；实际交接过几次后发现 40 万建议得太频繁或太晚（按实际改，并
在这里记下依据）。

## #16 · 同伴递来的因果说法（2026-08-27 / 08-28）

原 `secondhand-claims.md` 的全文并在这里。

技能里已经教你提防两类东西：**信号正常但事情停滞**（停摆四信号在「跑长命令」「已完工」「被 resume」三种情况下全读作
健康），以及**信号异常但事情健康**（「已关闭」不等于做完、grill agent 长时间 `idle` 是正常的）。第三类是从同伴 agent
那里收到的因果说法，它不是效率问题，是污染源：单 agent 里不核只是慢，多 agent 里不核就是把错误接进管道。

两个不同的机制：

- **传递不衰减（错误保值）**——一个错误说法经过一手不会变弱，措辞反而更肯定。人类协作里至少还有「你从哪儿听来的」
  这个本能，agent 之间没有。
- **每一手都是注入点（错误新增）**——错误不只是被转发，它可以在任何一手被新造出来。

2026-08-27 / 08-28 两天实际发生四次，两个方向各两次：

| 方向 | 说法 | 实际 |
|---|---|---|
| subagent → coordinator | 任务 X「前提已塌，建议关掉」 | 只塌了一半。描述里的问题段确实不成立，但候选做法段要的东西**不存在、是真活**，还带三个未决产品问题。照单接收就会关掉一件含真实需求的活 |
| subagent → coordinator | 「某个合并请求是 X 前提失效的原因」 | 实际是一个早得多的提交（引入一份 ADR），比那个合并请求早两个月 |
| coordinator → subagent | 「本周有五件活因为『待验收』状态标记而隐形」 | 实际 1 件。把「因标记隐形」和「关闭后标记脏」两种失效归成了一类 |
| coordinator → subagent | 「某个提交漏掉了项目说明文件里的测试计数」 | 那个提交明确豁免了它们并写了理由。看到「别处删了、这处还在」就推断成「教训没推广」，没读提交正文 |

四次里三次是被下游顶回来的（下游去核了原始证据），一次是自己回头核出来的。双方都不核，四次全都会落地。所以下游不是
转发管道，**它是唯一实际生效的检查点**——只在上游设防的规则会漏掉一半，还会让下游放松警惕。

「叙事变完整时最该核」这条：上面三个不成立的说法形状完全相同，叙事先成型、证据后补。三条分别让「标记卫生是系统性
问题」有了规模、让「预警起作用了」有了结局、让「同一个教训没被推广」有了因果。它靠自己的满足感触发，那个信号在错误
发生的当下就可感，不需要先识别出「这是一个因果说法」。

口径提醒：一篇复盘文章收尾写的「三次里有两次」是该文写作过程中遇到的，上表四次是那一轮盘面全部。两组口径不同，分开
放比合并强。

## #26 · 为什么不再用 `watch-workers.sh`（2026-10-21 合并 PR #2 时删掉）

**原文（已推翻）：** 09-28 夜里写的：每 15 分钟快照、有值得叫醒的变化就**退出**，用 Bash `run_in_background` 跑，退出

  `herdr-agents` 陷阱 ③a）。
- 只看 `visible` 的最后 4 行不够：在底部时 agy 的最后 4 行只有输入框和状态栏，看不出忙不忙。

## #29 · `scan-collisions.sh` 的旧版（2026-10-21 换掉）

**旧说法（patrol.md 原文）：** 「它扫主干 + 本机所有 worktree + 2 天内有提交的未合并远端分支，只报相对主干新增的迁移
revision id 与 ADR 编号」，迁移号「按 `revision = '…'` 那一行解析」。

**为什么不成立：**

- 只读 `revision`、从不读 `down_revision`，所以只抓得到「同号」，抓不到「编号不同但接在同一个点上」和「接在过时的
  head 上」——而合并后 alembic 双头正是这两种造成的（`0087` 那次两个迁移声明的上一个版本都是 `0085`，号不同也会双头）。
  `test-scan-collisions.sh` 用 `SCAN=<旧版> LEGACY=1` 能复现：旧版在这两个场景报「无撞号」、在所有撞号场景给的都是
  「先占者保号」。
- 扫本机所有 worktree，别的会话留下的旧 worktree 刷满噪音（2026-10 前任 coordinator 只好在外面套
  `grep -v worktree-agent-`）。现在由调用方决定哪些 worktree 是在飞的。
- 对每个 ref 把全部迁移文件逐个 `git show`，作者的一个私有项目上一次 34 秒、占满一个核；现在约 1 秒。
- 结尾提示「先占者保号」，和 patrol.md 的「先合并的保号」相反。

## #30 · 两次撞号事故与同号不同文件名的探针（2026-08-28）

**迁移 `0087`：** 被两条分支同时占，两边相差 62 秒合并，两个迁移声明的上一个版本都是 `0085`，主干出现两个 head，数据库
升级直接坏。一条 grill 分支先建、先占了 `0087`，但另一件活的 `0087` 后占却先合并，结果是 grill 那条改号成
`0089`/`0090`——这就是「先合并的保号」的出处。

**ADR `094`：** coordinator 从来没分配过 ADR 号，两条分支各写了一个 ADR-094，文件名不同、内容不同，git 把两个都干净地
合了进去（后写的已改为 095）。两边都没合并时没有合并顺序可比，才退化成先写者保号。
