# grill agent

[`SKILL.md`](SKILL.md) §3 报牌里放了 grill 选项、或用户挑中了 grill 时读这一页。

## grill 也起 agent，不在你自己的上下文里做

一次 grill 是长对话，做完你的上下文就废了，而你还得活着巡检。所以 grill 和实现一样，**派出去**。

在报牌那次多选提问里，除了可发的组，再放一个 grill 选项（同样受一屏 3 个的上限约束 —— 可发组和 grill
选项**共用**那 3 个格子，按当轮轻重取舍，并写明各自还剩几个没上屏）。

用户挑中之后：

```bash
herdr worktree create --cwd <repo根> --branch grill/<议题短名> --base main \
  --label "GRILL #<N> · <短名>"                       # 命名见 SKILL.md「命名与标记」
herdr tab rename <tab_id> "GRILL #<N> · <短名>"
herdr agent start grill-<N>-<短名> --kind claude --pane <root_pane> --timeout 60000 -- --model opus
# 【必须】确认就绪再发 —— 按 herdr-agents §1（轮询 visible 到 banner，按掉信任对话框）
herdr agent prompt grill-<N>-<短名> '/grill-with-docs <这批活的号 + 你卡在哪个判断上>' \
  --wait --until working --timeout 12000
# 报 agent_prompt_stalled ⇒ 重发；返回 OK ⇒ 什么都不能证明 —— 按 herdr-agents §2 回读 + 内容计数
```

`/grill-with-docs` 是一个做 grill 的技能的例子，换成你装的那个。**斜杠命令经 `agent prompt` 打进去是有效的**，
即使那个技能带 `disable-model-invocation: true`（`herdr-agents` §2）。

（这里的启动写法早先是 `pane read --source recent-unwrapped --lines 20` 加一个待定的 banner 特征串；
那种读法在新 worktree 的信任对话框上读回全空，见 `herdr-agents/startup-evidence.md` §①a，所以改成指向
`herdr-agents` §1 的统一序列。）

## 八条硬约束，全部要写进给它的指令里

1. **同一时刻只起一个 grill agent。** 用户是一个人，两个 grill agent 同时向他们发问，会被撕成两半 —— 这跟
   「不微操」是同一个道理。
2. **给 grill agent 的那批活应当彼此相关。** 相关议题会互相澄清，一次谈完比分三次谈便宜。判据和分组一样：
   共享模块或共享概念。
3. **它必须把结论写回工作流的追加记录**（Q3），而且按工作流的规矩办（例如不重写最初的描述）。这是闭环的
   唯一接口 —— 结论只留在 grill agent 的对话里，等于没发生：那个 agent 一关，下一轮勘察什么都读不到，那件
   活会再次落进「需先 grill」桶。
   **结论要写到「另一个 agent 只凭它就能实施」的程度**，因为接手的正是这样一个 agent（见下节）。它当中该有：
   拍板了什么、否掉了什么及理由、以及谈出来的**影响面**（会动哪些文件/模块）。最后一样对下一轮分组是必需的。
4. **grill agent 不写实现代码。** 它可以改文档目录（ADR、领域术语表 —— 那是 grill 技能的本职），不碰实现
   代码目录。
5. **有文档改动就自己开交付物，开成未完成状态**（Q3）。别等文档谈完就转正——转实施在同一条分支上继续做，
   完工后再转为完成状态，文档和实现一次合并。没有交付物就没有东西可以转正，转实施也无处挂。
6. **它的第一条消息必须是背景交代，且不含任何提问。** 要说清四件事：这件事是什么、系统现在是怎么做的、为什么
   现在要谈它、不谈会怎样。**提问从第二条消息才开始。**
   **判据：第一条消息里出现问号或选项 = 违反。** 这条之所以写成这个形状，而不是「先介绍一下背景」，见下面
   那节。
7. **每个选项的第一句必须说「选了它以后会发生什么变化」** —— 对用这套系统的人、对业务、对以后要维护它的人。
   技术机制不是不能写，是**不能写在第一句**，而且要有一个明确的分隔（写成 `怎么实现的：……`），让用户只读
   上半截就能做决定。
   **判据：把每个选项的第一句单独拎出来，它必须是用户不看代码就能判断好坏的句子。** 出现 helper、扫表、判定、
   返回值这类词就是没过。
   同一个方案的两种写法（2026-09-01 真实例子，前者是实际发出去的）：
   - **机制写法（违反）**：「A′ — 角色集合命中判定。一个 helper：扫 active assignment，命中管理角色集合就
     返回『不适用』。」
   - **后果写法（合规）**：「以后每新增一个岗位，都要有人记得把它归进『算不算加班』的名单；漏了就会静默地
     按普通员工计算。好处是今天就能做完。」
8. **一个选项如果无论如何写不成后果，那它就不该拿去问用户。** 这不是文笔问题，是**问错了高度**：写不出「对人、
   对业务有什么不同」，说明这是个纯技术决定。**grill agent 自己拍板**，并在写回的结论里记下拍了什么、为什么
   ——不要包装成选项推给用户。
   这跟「需先 grill」桶那条判据（「实现方式取决于一个产品/领域判断，不是技术判断」）是同一把尺子，只是用在
   两个粒度上：那条决定**一件活该不该 grill**，这条决定**一次 grill 里的某个岔路该不该问**。
   **三条里第 8 条最先生效**，它会顺带减轻另外两条的负担：不该问的问题不问了，剩下的自然更容易按第 7 条写清
   后果，第 6 条要交代的背景也少一截。

**报它的位置和报 worker 一样**（见 `SKILL.md`「发完必须告诉用户去哪看」）—— 而且 grill agent 更需要，因为
用户必须亲自到那个 pane 里跟它对话。

## 第 6–8 条为什么写成可检查的形状，而不是「要说人话」

**出处：2026-09-01 用户的原话。**

> 得更新一下 dispatch 的 skill。grill 时，agent 会扔一大段技术描述，然后给我选项。我完全看不懂
> 在说些什么。有两个要求，一个是 grill 前先介绍一下故事背景。然后 grill 过程中要说人话。

说的是一次真实的多选提问：一个 grill agent 给了三个选项，正文就是第 7 条里那个「角色集合命中判定」的写法。
**技术上准确，但读不出选哪个会发生什么。**

**不要往这里加第九条「要说人话」。这件事已经试过两次，两次都无效，第二次是量出来的。**

1. **当时那个项目的说明文件第一行就是「和人沟通的时候要讲人话」**，每个 session 都加载。上面那段技术描述
   **就是在这条规则已经躺在上下文里的情况下**写出来的。
2. **那个项目的两份 agent 说明文件曾各有一节 "Requirements discussion style"**（"explain concepts in
   plain, everyday language first. Do not lead with document-style sections, implementation
   terminology, data models, or proposed schemas."），**2026-08-25 被一次提交删除**，理由是实测无效：
   49 份 transcript、1236 条实际展示给用户的消息（41.1 万字符）里，每千字有 22.9 个需要仓库记忆才能解码的
   token，每 117 字符出现一个裸 `#N`，67% 的中文句子里嵌着英文标识符；而且**用户在 2026-08-21 第四次说看
   不懂之后，这个密度的中位数不降反升（19.2 → 21.4）**。当时一并**否决了为它加 hook**——结论是改在行为上，
   不在措辞要求上。

   **那次删除的理由只活在那个提交的正文里，主干上任何文档都查不到。** 所以下一个人会好心地把「要说人话」
   再加一遍——**这一段就是拦住他的唯一记录，别删。**

所以往这三条上再加东西时，用同一把尺子量：

> **你加的每一条，要能回答「读者怎么知道自己违反了它」。**
> 「写得通俗些」回答不了；「第一条消息不许出现问号」回答得了。

这也是「不变量要落在你的循环里」那条原则在措辞上的同一副面孔：一条**无法被判定**的要求，和一条挂在 worker
记性上的要求一样，失败时是无声的。

> 写下时这三条只有 2026-09-01 这一次事故支撑，**尚无第二轮实跑**——形状对不对（尤其第 8 条会不会被拿去
> 回避该问的产品问题）要用过几轮再回来看，先别当定案。

## grill 完在原分支继续做

**2026-08-26 用户当面改掉的流程：** 文档交付物开成未完成状态，**同一条分支继续实施**，完工转正，一次合并。
旧流程「grill 交回来，重新派 worker 从主干开分支」已作废——那道门要防的东西（实施者看不到未合并的 ADR）在新
形状下根本不存在：ADR 就在实施者自己的树里。

**旧流程里的两条规矩不是仪式，继续生效，只是执行的时机变了：**

1. **实施前必须占住。** grill 阶段不需要占住，一旦转入实施就需要——即使还是同一个 agent、同一条分支。
   2026-08-26 实跑：一批三件活在开始实施前都是「还没占」，也就是说盘面上没人知道这几件活正在被做，不占住
   就是结构性隐形。分支名沿用 `grill/<议题>`、不改成 `fix/<N>`——**接受现状**，但占住记录里的分支名必须
   与它一致（Q4），否则会被同伴当成过期的占住抢走。
2. **冲突复检不取消，只是提前。** 让 grill 交回来这条旧规矩，真实理由从来不是「上下文干净」（那只是次要
   好处），而是：**这件活的影响面刚刚才第一次变得可算，必须拿去和盘面上所有在飞的分支重新比一遍**——它当初
   进「需先 grill」桶正是因为算不出来，现在算得出了就必须做这一步，否则可能正好撞上某个已经在跑的 worker。
   **这一步没有消失**，只是从「切新分支前」挪到了「开始实施前」，由 coordinator 在批准转实施时做。跳过它，
   等于把本技能存在的唯一理由跳过了。

**grill agent 自己接着实施，带来一个新的、必须正面处理的风险：它的上下文塞满了拉锯和被否掉的死路。** 自己
实施时，它可能重新权衡已经关闭的选项，或者因为实现起来麻烦而回头改结论。应对办法（2026-08-26 实测有效）：
转实施的指令里**逐条列出被否掉的选项并声明它们是关闭状态**，同时给一个出口——**若某条结论技术上不成立（不是
不方便，是不成立），停下来回报 coordinator，不要自己改判**。「不方便」与「不成立」的区分是关键：前者仍然
照旧执行，只有后者才允许停下。

角色从 grill 变成 worker，三处标签要跟着改，否则盘面上仍显示为 GRILL：workspace 标签、tab 标签从
`GRILL #…` 改成 `WORKER #…`，agent 名同步改（`herdr agent rename` 可用，2026-08-26 实测）。

所以第 3 条硬约束（结论写回工作流的追加记录）不是流程规定，是**承重墙**：下一个 agent（无论是原 agent 转正
后的自己，还是万一它死掉之后重新派来的人）能否只凭那段记录把活干下来，就是「grill 是否真的谈透了」的检验。
写不清楚 = 还没完。
