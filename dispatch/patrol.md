# 巡检

[`SKILL.md`](SKILL.md) §5 的全文。**每一轮都要过完这里的每一项**；某项这一轮查不了，写「未查：原因」，不许
不提。纯观察模式（用户一组都没选）下，这是你唯一要做的事。

## 巡检由什么触发

**「每一轮」要有东西来开始它。** 这份文件之前只写了一轮要查什么，没写一轮由什么开始、多久一次。
2026-09-28 下午的后果：coordinator 只在用户说话或子 agent 回报时才去看；一个 agy worker 停在屏幕上
提问等人回答，没人知道，直到用户自己发现。worker 叫不醒你——agy 够不着 `SendMessage`，Claude Code 的
跨 session 消息会被扣留、超时静默丢弃（`herdr-agents` §5）——而且最该报的情况（卡死、被杀）它本来就
报不了。**所以叫醒你的东西必须在你这一侧。**

### 三件事，缺一件就说出来

与 harness 无关，coordinator 需要：

1. **叫醒源**：不靠用户、不靠 worker，在「值得看」的变化出现时叫醒你。用一个不调用模型的看门脚本
   （`scripts/watch-workers.sh`）轮询地面事实，有变化就退出，退出即叫醒。
2. **兜底时钟**：比叫醒源慢的完整巡检（本文件全部各项）。它的**第一项是确认叫醒源还活着**，没活着就
   重启。它还兜住看门脚本判错的情形——下面「实测」里，看门脚本漏掉的三次都是兜底巡检抓到的。
3. **事件触发**：交付物合并、有新交付物打开、用户开口——立刻重扫，不等时钟（见下文 `scan-collisions.sh`
   那节「触发点不止每轮」）。

你的 harness 做不到 1 或 2 时，**每次回复都写一句「现在没有自动巡检，只在你说话时我才会去看」**。不许
让用户以为有人在看而其实没有——那正是 09-28 下午的样子。

### 什么值得叫醒你

2026-09-28 15:38 → 09-29 05:31，看门脚本一共退出叫醒 39 次（逐条对 coordinator transcript 归的类，
人工归类，个别条目可能 ±1）：

| 信号 | 叫醒？ | 实测 |
|---|---|---|
| 进程没了 / agent 出现或消失 | 叫 | 当夜没有一次是 worker 意外死亡；出现/消失**全是 coordinator 自己起停 worker 引起的**，连同改完脚本后状态文件对不上的那次，共 7 次叫醒是自己的动作——用 `--rebaseline` 消掉，见下。不因此降级：死亡本来就少，但一旦发生是最该知道的 |
| 交付物状态变（开了 / 合了） | 叫 | 开 PR 的 9 次全部有用；合并 1 次（用户合的，coordinator 已知） |
| 屏幕**进入**「等人」 | 叫 | 有用的多数来自这一类：做完等验收、排队消息没被取（01:32）、模型接口报错停住（03:58、04:44） |
| 模型接口报错停住（agy `Internal error encountered`） | 叫 | 单列，因为 herdr 与只看「在不在干活」的规则都把它读成 working，见下 |
| 新提交（head 变） | **不叫**，静默记下 | 单独因提交叫醒的 4 次全是噪音；09-29 01:34 起不再因提交叫醒 |
| 从等待回到干活 | 不叫 | 09-28 16:09 那次是噪音，当场改掉 |
| 停着、但在等**它自己起的**测试/构建跑完 | 不叫（`WAITING-BG`） | 02:32、03:59、04:00 三次误报都是这一类，另有 4 次混在有用的叫醒里；agy 的后台任务跑完后它会自己接着干 |

**什么观测会推翻这张表**：某个「不叫」的信号背后出现过一次真的需要人的情况（例如 worker 在
`WAITING-BG` 里等的任务早已跑完，它却没有自己接着干）——那就把它挪回「叫」；某个「叫」的信号连续一整轮
（一夜）全是噪音，就挪到「不叫」并在这里记一笔。

### 屏幕怎么判「在干活 / 在等」

**读哪块屏幕：`herdr pane read <p> --source detection`**——herdr 自己做状态检测用的那块底部快照，不受
滚动位置影响（herdr 0.9.1 文档「Reading panes」）。看门脚本 2026-09-29 起改用它。

- **被推翻的旧读法 1：`--source visible` 取末 4 行。** 09-28 夜里 coordinator 认为 `visible` 会读到旧画面，
  改成了 `recent --lines 12`。这个判断当时没隔离验证，**同一时期的另一个误判（下一条）也在起作用**，而
  `herdr-agents` §3 在 0.9.1 上观测到 `visible` 返回的是当前一屏。是不是 `visible` 的问题，另有调研在查；
  在它有结论之前，不要拿「`visible` 会读旧帧」当规则，也不要回到 `visible`——`detection` 是专门为这件事
  给的读法。
- **被推翻的旧读法 2：「底部有 `N task(s)` 就算在干活」。** 09-28 下午加的，理由是 agy 跑长命令时底部显示
  `N task(s)`。错在：这个数字是**后台 shell 的个数**，dev server 一直在跑，它就一直大于 0。09-29 00:45 起
  A1/A2/B/C 四个 worker 写完文档停在检查点等 coordinator 验收，这条规则把它们一直读成 working，**看门脚本
  一小时没出声**，是 01:15 的兜底巡检发现的。09-29 01:16 删掉。**herdr 自己的 agy 规则正是这么写的**
  （`background_tasks_working`，见 `herdr-agents` §3 陷阱 ③a），所以 `herdr agent list` 的 `agent_status`
  对 agy 同样不可信——别拿它替代屏幕判定。
- **现行规则**（`watch-workers.sh` 里的 `classify`，2026-09-29 用当夜截下的五种屏幕逐条测过）：
  底部 4 个非空行里有中断提示（agy `esc to cancel`、claude `esc to interrupt`、opencode `esc interrupt`）
  = 在干活；否则按顺序认权限对话框、`Internal error encountered`、`Press up to edit queued`、
  「有测试/构建类后台任务在跑」（`WAITING-BG`），都不是就是 `WAITING`。
  **推翻条件**：某个 kind 干活时底部不再出现中断提示（会被读成 WAITING，叫醒次数突然变多）；或者
  herdr 的 agy manifest 修掉了 `background_tasks_working`、并能认出接口报错——那时改用 herdr 的状态，
  删掉脚本里自己的屏幕规则（上游能用就不自己维护一份）。

### 间隔

- **看门脚本：默认 15 分钟**（2026-09-28 用户定的）。它不调用模型、只在有值得叫醒的变化时退出，所以间隔
  决定的是「worker 停下来等人」最多被晾多久，不是花多少额度。当夜被晾最久的一次（上面那一小时）是规则
  错，不是间隔长。**推翻条件**：出现一次「worker 等人、规则判对了、却因为间隔晾了 15 分钟造成了返工」，
  就调短；调短后若出现大量「进入等待又马上恢复」的短暂叫醒，说明屏幕判定对中间态太敏感，先修判定。
- **兜底完整巡检：30 分钟**。当夜 27 次里大约 19 次「无变化」，有产出的 8 次里 3 次是抓到看门脚本漏掉的
  停顿，其余是看门脚本本来就不查的东西（合并演练里的 `login.ts` 冲突、worker 跳步骤、PR 内容问题）。
  **没有 worker 在飞时暂停兜底巡检**（09-28 20:15 → 23:45、09-29 05:45 → 08:10 全是空转，coordinator
  自己在 23:45 提过要不要停）；有 worker 再开。

### 在 Claude Code 里怎么做（2.1.283 实测，文档核于 2026-09-29）

| 机制 | 用来做什么 | 限制（会咬人的） |
|---|---|---|
| Bash `run_in_background` 跑 `watch-workers.sh` | 叫醒源。脚本退出 → 一条完成通知，空闲时直接开新一轮，忙时插进当前轮 | 没有时间上限；**每次退出都要你重启**；session 退出或 `--resume` 后**不恢复** |
| `CronCreate`（或 `/loop 30m …`） | 兜底完整巡检 | 只在空闲时触发（忙就顺延，不补发）；**固定偏移**：文档写「最多晚半个间隔」，工具自带说明写「最多晚 10%」，实测 `7,37 * * * *` 每次都在 `:14:48 / :44:48` 触发（晚 7 分 48 秒）——以文档为准；7 天过期；session 关了就没；`--resume` 会恢复 |
| `Monitor` | 可替代 Bash 后台：脚本不退出、每行变化一条通知 | 每次最长 30 分钟，到点要重新挂——和「每次退出后重启」是同一种负担，没有省事 |
| Stop hook 读 `background_tasks` | 可选：一轮结束时若看门脚本不在后台任务里，挡住结束并提醒重启 | 只在 Claude Code 有；没实测 |

- **重启看门脚本别靠记性**：每个叫醒通知处理完的最后一步是重启它；兜底巡检第一项再核一遍。当夜 40 次
  重启，间隔中位数不到 1 分钟；最长两次是 9 分钟（18:33 coordinator 额度用尽）和 12 分钟（19:11 的叫醒
  通知入队后 12 分钟才被处理，原因没查清，**一次观测**）。
- **停脚本用 `watch-workers.sh --stop`（按 pid 文件），不要 `pkill -f <片段>`**：`-f` 匹配整条命令行，那条
  `pkill` 所在的命令自己也含这个片段，会被一起杀掉——当天发生了三次（17:19、18:57、19:36）。
- **同时只许一个实例**：09-28 17:49 用 `& disown` 起过一个收不到通知的副本。脚本现在用锁拒绝第二个实例。
- **自己起停 worker 之后先 `--rebaseline`**，再重启：否则下一次叫醒是你自己的动作（当夜 7 次）。
- **机器睡眠时什么都不跑**：09-29 07:04 → 08:10 系统日志空白，这段兜底巡检一次没触发，醒来后补了一次；
  09-28 20:15 → 22:44 同样没触发（那段没有日志可核）。worker 进程也一起停，所以只是延迟，不是漏看；
  要整夜跑就别让机器睡。

### 其它 harness

没有「后台命令结束就叫醒」的 harness：让 coordinator 在前台跑 `watch-workers.sh`（它本来就在等），用那个
harness 的命令超时当兜底时钟，超时返回就过一轮完整巡检再接着跑；代价是等待期间用户要先打断它才能说话。
这条**没在任何 harness 上实测过**，用之前先测一次「超时返回后能否自己接着跑」。两样都做不到，就按上面
「缺一件就说出来」办。

## 死活、状态、有没有被重启

- `herdr agent list` —— worker 退出后会**从列表里消失**，pane 变 `unknown`。死活可判。
- **对每个活着的 worker 读回滚佐证**，不能只信 `agent_status`（`herdr-agents` §3 陷阱 ③）。
- **判定「停摆」前四个信号必须全部为真**（transcript 静止、文件 mtime 静止、无存活子进程、分支上没有未合并
  提交也没有已开的交付物）——为什么少一个都会误报、以及实测的两次误报，见 `herdr-agents` §6。交付物那一项
  按工作流去查（Q3/Q4）。
- **每轮巡检比一次 pid**：worker 自报的进程号对上那个 worktree 里实际活着的进程，不等就是被 `claude --resume`
  重启过——四个停摆信号在重启前后全部读作健康，只有这一项会翻。检测命令、为什么不用启动时间、重启后怎么
  补发，全在 `herdr-agents` §6「被 `claude --resume` 重启过」。（这也是下面「否定结论会腐烂」的一个实例。）

## 五问

每轮回答这五个问题，自己决定怎么查：

1. **归属**：每个在办的活，真实状态是什么？有分支/交付物吗？谁在做，还活着吗？——以地面事实为准（进程、
   工作区、提交、交付物），不要相信工作流里的状态标记。
2. **偏差**：记录说的和事实说的，哪里不一致？两栏并排列出。
3. **冲突**：在飞的分支之间、以及它们和主干之间，有什么会在合并时炸的东西？重点看**共享且带顺序或唯一性
   约束的东西**——迁移号、生成的 ID、锁、版本号、注册表。这类冲突通常不表现为文件冲突。
4. **僵尸**：哪些分支/工作区/任务已经没有意义了？
5. **阻塞**：谁卡着谁？

它们已经覆盖了「隐形冲突」那一类，不要重写。**一处例外要认清**：第 3 问已经点名「迁移号、生成的 ID、锁、
版本号、注册表」，但它是一道**要你自己想办法去查**的问句 —— 两次撞号（一次迁移双头、一次 ADR 撞号）都不是
巡检发现的，是事后炸出来的。下面那条 `scan-collisions.sh` 是把第 3 问变成一条真的会跑的命令，**不是另立一条
规则**；反过来也别用「第 3 问我想过了」代替那次扫描。

五问的不变量（任一不满足，停下来说「我的方法有问题」，不要输出报告）：每个在办的活必须落进某一类，不允许
「没查到」；任何「没有冲突」的结论必须说清用什么判据测出来的，**「没报错」不是证据**；解析不出来的值显式
报错。结论要能被复核，数据会在你分析途中过期，发布结论前重读一次。

## 占住状态

- 对不归你管的 session，也按工作流读占住状态（Q2）。工作流的结构化占住记录是唯一跨 harness 的活性判据。
- **读到「活性未知」时活性无从判断** —— 此时唯一权威是工作流自己的过期规则（例如「分支 2 天无提交」），工作流
  的检查通常会连同分支状态、未合并提交数、交付物状态一起给你。**绝不能把「未知」读成「死了、可以抢」。**
- 盘面上可能有大量旧格式的占住记录（写下时没有 socket 字段），一律读成「未知」（2026-08-25 实测两件活皆如此）
  —— 这是设计如此，不是故障。随着各 session 改用新格式重新占住，这一条会自然消退。

## 做完没有，以地面事实为准

- **「已关闭 / 已完成」不等于做完了。** 有的工作流会被关联动作自动关掉一件活，绕过验收；有一件活就是「已关闭 +
  已完成」而 worktree、分支、已退出的 session 全在盘上。以地面事实为准。

### 容器没人关

**同一个病灶反过来出现在容器上：不是「关了但没做完」，是「做完了却没人关」。** 步骤 1 的候选清单把容器全部划进
「不可发」，这个排除是对的，代价是容器的完成度从此对 coordinator 不可见——子项各自完成之后没有任何东西回头看
容器。巡检要另跑一次容器扫描（QB；工作流的技能会给查法），分三个桶：

- **子项全完** → 判断能不能关，见下；
- **部分完成** → 剩余子项本来就在候选池里，补一句「这是某容器的最后一块」，报牌时要用（`SKILL.md` §3）；
- **零完成** → 不动。

**子项全完也不能直接关——先读容器自己的描述，判断它是不是纯容器。** 2026-08-28 巡检查出三个子项全完的容器
（5/5、9/9、2/2）一直挂着没人关：前两个的描述明写「不要直接认领或实现它」且「最后一个子项合并后关闭」，不带
自己的验收标准，子项全关即可关。**第三个不是这样**——描述带自己的四条验收标准，逐条核实后第四条只做了一半：
一份新 ADR 声明取代一份旧 ADR，但旧的没有按那个仓库的先例指回来，缺口立成了一件新活。**按「子项全完就关」处理
会把它直接关掉，那个缺口永远不会被发现——两种判法这次给出了不同结果，差出来的正好是一个真缺口。** 带验收标准的
容器必须逐条核实，通不过的部分单独立牌，收尾记录写明哪条过、哪条没过、依据是什么。

## grill agent

- **grill agent 长时间 `idle` 是正常的，不要当成卡死。** 它在等用户回话，那可能是几小时。判它是否真的结束，
  看**结论有没有写回工作流的追加记录**（Q3）—— 那才是它的交付物，不是它的状态。没写就还没完，哪怕它已经安静了
  很久。
- **一个 grill agent 结束后**（结论已写回），下一轮勘察会把那批活移出「需先 grill」桶。此时才可以起下一个
  grill agent —— 同一时刻只许有一个。

## 未完成交付物的年龄

新流程下（`grill.md`「grill 完在原分支继续做」）阻塞没有消失，只是换了位置：未完成的交付物迟迟不转正，ADR 就长期
不进主干，任何从主干开分支的人依然看不到它。一个长期未完成、且分支上没有新增实施提交的交付物，等于 grill 的成果被
锁住了——按工作流列出未完成交付物，配 `git log --oneline origin/main..HEAD` 查，发现了就去问那个 worker 卡在哪，
别等它自己冒出来。

## 稀缺顺序标识符撞号：每轮跑一次 `scripts/scan-collisions.sh`

```bash
MIGRATION_DIR=<迁移目录> ADR_DIR=<ADR 目录> scripts/scan-collisions.sh [--no-fetch] [--days N]
```

两个目录由项目说明文件给出；都不给时脚本报错退出，不会假装「没撞号」。退出码 0 = 无撞号，1 = 有，9 = 脚本自身
出错（三者分开，是因为「停摆」那条记的那两次误报正是崩溃与真实告警在退出码上分不出来）。它扫主干 + 本机所有
worktree + 2 天内有提交的未合并远端分支，只报**相对主干新增**的迁移 revision id 与 ADR 编号，并且**迁移号按文件
内容里的 `revision = '…'` 那一行解析，不按文件名**（写下时支持的是这种 Python 迁移文件格式；别的迁移工具要改脚本里的
`parse_rev`）。

为什么必须由你在循环里扫：这类冲突**文件路径不重叠、git 合得干干净净**，两次都是合并之后才炸的 —— 迁移 `0087`
被两条分支同时占，两边相差 62 秒合并，两个迁移声明的上一个版本都是 `0085`，主干出现两个 head，数据库升级直接坏；ADR `094`
更隐蔽 —— coordinator 从来没分配过 ADR 号，两条分支各写了一个 ADR-094，**文件名不同、内容不同，git 把两个都干净地
合了进去**（后写的已改为 095）。

**最阴的一种是同号不同文件名** —— 与主干上的，或两条分支之间；`git` 对这一种连冲突都不报。2026-08-28 用探针文件
实测两种都报得出来：ADR `095` 与主干上同号而文件名不同、迁移 `0089` 被一个 `9999_probe.py` 与另一条分支的
`0089.py` 同时占（文件名不同，靠解析文件内容才抓到）。

发现撞号：**先合并的保号，后合并的让路**——不是先占者保号。上面迁移 `0087` 那次，一条 grill 分支先建、先占了
`0087`，但另一件活的 `0087` 后占却先合并，结果是 **grill 那条改号成 `0089`/`0090`**，不是后占的那条改。ADR `094`
那次两边都没合并，没有合并顺序可比，才退化成先写者保号。改掉的号若已被任务记录引用，连带更新引用。**自己协调
不了才升级给用户。**

**触发点不止「每轮」这一个时钟**（时钟本身怎么来，见上文「巡检由什么触发」）。别等定时扫描——**交付物合并**（作废所有「vs 主干」部分）与**有新交付物打开**
（只需要核它 vs 每个已核过的）这两个事件也应该让你立刻重扫一遍，两个触发点合起来能把滞后压到一个事件以内。
（对应下面「否定结论会腐烂」里的三行表。）

## 否定结论会腐烂，肯定结论不会——但要分清「什么」腐烂

「有问题」永远为真；「没问题」看是对什么下的判断——**冲突是两两对称关系，不是集合属性**：「A 与 B 撞号」和
「A 与 B 没有资源冲突」都是关于**这一对**的事实，只要 A、B 内容不变就不变。新来一个 C 只新增 (A,C)、(B,C) 两个
未核的对，**不作废已核过的 (A,B)**。真正让一个已核结论作废的只有三件事：

| 事件 | 作废什么 | 要核什么 |
|---|---|---|
| 新交付物打开 | 什么都不作废 | 只核新来那个 vs 每个已核过的；撞了标新来的那个 |
| 有交付物合并（主干前进） | 所有未合并交付物的「vs 主干」部分 | 重核剩下的未合并交付物（工作流给的「可合并」信号可作辅助） |
| 某交付物推了新提交 | 关于那一个的一切结论 | 只重核它 |

这条原则仍有三个不因上面这次修正而失效的实例：项目说明文件里一个测试用例数被固化成看起来永久有效的数字；一个
「待验收」状态标记让一件活隐形约 38 小时（一个当时正确的状态，事情做完后没人撤）；上面「停摆」的四个信号在跑
长命令/已完工/被 resume 三种「正常」情形下同样为真——**同一个病灶，不同的发病部位。** 下面「三种核查标记」与
「合并计划」都是这条原则的应用，但分工不同：**标记**管本交付物自身足迹与已核过的两两关系（稳定，不因新交付物
打开而作废）；**合并计划**管顺序（只在被问的那一刻算，顺序一变谁让路就变）。

## 三种核查标记

发现资源冲突、顺序依赖，或核完确认无害后，挂在交付物上（QA，工作流的技能给出具体标记名），不要只留在自己的
上下文里：

- **占稀缺资源** —— 本交付物消耗了迁移号 / ADR 号 / 注册表项 / 端口。
- **需按序合并** —— 本交付物有硬性前置（例如它的迁移声明的上一个版本，是另一个尚未合并的交付物才建的）；
  前置是谁、为什么，写在评论里，不写在标记本身。
- **已核**（绿色）—— coordinator 已核过本交付物的资源足迹与两两冲突，**结论写在评论里**（含基准 commit 与时间）。
  持久有效，直到本交付物推新提交、或主干前进（见上表）。

三态：已核 = 看过了、去读评论；占稀缺资源/需按序合并 = 看过且发现了东西；**无标记 = 尚未核，不要当成干净的**
——这是那次修正的目的：之前只标危险，导致「无标记」同时可能是「核过且干净」和「还没核」，从列表上分不出来。

「已核」覆盖的是**机械项**（顺序标识符、文件两两重叠、注册表项在几处对齐），**不等于「已核正确性」**——契约
形状与语义耦合只能靠读，读不全，例子见下面「合并计划」。

仍未解决的弱点：**coordinator session 死了**，新交付物会一直没有标记——「无标记」于是同时意味着「刚开还没核到」
和「coordinator 挂了」，三态没有消掉这层歧义，只是降了一层。能做的是在报告里说清 watcher 是否还活着，如实写在
这里，不要假装三态就完备了。

两条要点：

- **只有你打，不要求 worker 打。** 理由与「不变量要落在你的循环里」同源：worker 模型各异、上下文预算不同，读没读完
  指令不可验证。
- **配一条评论放细节**：占了哪些号、与哪几个在飞交付物改了同一批文件、顺序约束或核过的结论——评论是稳定内容，
  交付物一旦开出就不太会再变，细节留在评论里比留在标记本身经得住时间。

> 本节来自用户 2026-08-28 的决定，**尚无实跑事故支撑**——「占稀缺资源」/「需按序合并」截至写下时只用过一次
> （结论是「不该打」，只验证了「不打」这条路径）；「已核」是同一机制两小时内的第二轮修正。**这套标记规则本身
> 正在迭代，用过几次后应当再回来看**，不要当成定案。

## 合并计划：在决策点现给，不落成持久标记

用户要的是「这一组现在合安全吗」，而那个答案**只在被问的那一刻有意义**——这是「否定结论会腐烂」在合并场景的
具体应用。格式：一份带**基准 commit 与时间**的短清单（当前未合并交付物、哪些互相冲突、建议顺序、什么卡在什么
后面），在未合并交付物集合变化时刷新、在被问时交付，**不挂在任何交付物上**。

写清楚你能核到什么程度：

- **机械可核（强）**：顺序标识符、改动文件两两重叠、注册表项在几处对齐。
- **需要读、尽力而为（弱）**：契约形状冲突、语义耦合（例：一件活需要把新字段喂进另一件活造的一个预览用合成
  对象，否则实时预览永远显示占位符，而 **类型检查通过、测试不红**——那是读出来的，不是扫出来的）。

**「已核资源冲突」不等于「已核正确性」。**

## 2026-09-17/18 实测补充（一轮八张牌跑下来，每条都有当场证据）

### 分支落后主干会静默删掉别人的文件

那一轮真实发生：一件活的分支建于另一件活合并之前，于是它相对主干的 diff 显示一个模块和它的测试文件**被删掉
1507 行**。不是谁删了，是那条分支还没有这两个文件。**照这样开交付物会把已合并的活整个回退，而且 git 不报任何
冲突、review 里也极难发现**（那两个文件根本不在实施者的视野里）。

所以派牌给一条**已存在的旧分支**时，第一步必须是 rebase 加一句自检，写进 prompt：

```bash
git fetch origin && git rebase origin/main
git diff --stat origin/main..HEAD    # 别人的文件不能出现在这份 diff 里
```

单个 worker 抓不到这一类——它只会 review 自己改过的东西。这是 coordinator 的活。

### 两条分支改同一批验收数字时，先合「新真值」那条

两件活都改同一个测试文件：一件换了计算口径，改了 +202/-160（口径变了，数字几乎全部重算）；另一件修一批测试
红，改了 +50/-14（基于旧口径的部分修复）。**先合换口径那件、另一件再 rebase** 才对：反过来是让换口径那件去解
一堆注定被丢弃的冲突。
判据不是先来后到，是**谁的版本是改完之后的真值**。

那一轮实际合成了反序，代价是换口径那件多做一轮 rebase + 重跑一次 8 分钟全量测试。

### 主干全绿之后，验收标准要跟着抬

主干红着的时候，worker 的合理交付是「新增失败 0 条」加两份可对比清单。主干一旦全绿（那一轮在一件修测试的活
合并后达成：`4224 passed / 0 failed`），**这个论证就不再成立**——没有已知红可以垫底，分支必须自己全绿，有红
就是它的。
这条要在派牌时写进 prompt，因为 worker 看不到盘面、只会沿用上一张牌的口径。
